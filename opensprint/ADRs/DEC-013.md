# DEC-013: Rule Links Are Harvested From Code, Not Declared in Records

## Question

[[DS-LOOP-CLOSURE]] requires knowing whether a decision is guarded by a rule. Should records declare the rules that guard them, or should the link be discovered from the codebase?

## Decision

Rule links are harvested by scanning the codebase for records cited in tests and checks. A rule declares what it guards, by citing the record id; the record says nothing about its rules.

An agent-executed playbook counts as a rule on the same terms — it cites the id.

## Consideration Factors

| Factor | Weight | Harvest from code | Declare in the record |
|---|---|---|---|
| Matches existing practice | HIGH | 69 of 96 cashier test files already cite a record; 16 of 26 codex rules do ✓ | Only 4 of 64 ADRs cite a test, and no frontmatter field links one ✗ |
| Staying accurate | HIGH | The link lives next to the code and moves with it ✓ | A record must be edited when a test is renamed ✗ |
| Detecting dead guards | HIGH | A rule citing a superseded record is visible ✓ | Same, if maintained ✗ |
| Coverage of driver-specs | MED | Indirect — via the answering ADRs ✗ | Direct ✓ |

## Rationale

The data settles this. Records almost never point at their tests; tests very often point at their records. Harvesting reads links that already exist instead of asking anyone to maintain a second set. Across cashier it covers 50 of 64 ADRs with no new authoring at all, and every id cited by a test resolves to a real record.

Driver-spec coverage is indirect, and that is correct rather than a shortfall. Only 4 of 17 cashier driver-specs are cited by a test directly, yet `DS-MULTI-TENANT-ISOLATION` is fully guarded — its tests cite `DEC-005`, `DEC-014` and `DEC-033`, the decisions that answer it. "Is this constraint asserted?" is answered by following the graph: a rule cites a decision, and the decision depends on the constraint.

## Invalidation Trigger

If a project's tests do not cite record ids, harvesting yields nothing and the loop cannot close mechanically there. The response is a convention for citing ids in tests — the practice the data shows already works — rather than moving the declaration into records.
