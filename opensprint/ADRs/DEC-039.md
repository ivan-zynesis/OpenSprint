# DEC-039: `/opsp:triage` Is Its Own Tool, for Explicitness Rather Than Necessity

## Question

[[DEC-034]] adds `/opsp:backlog`, so a backlog item exists holding an Objective and a Goal. Picking one up and working it into a formal proposal requires strategy brainstorming. `/opsp:propose` would do that naturally — when the persisted item is insufficient for a structured proposal, it simply continues the conversation. Does that phase need a tool of its own?

## Decision

Yes. **`/opsp:triage`** picks up a backlog item, decides whether to advance it, and conducts the strategy brainstorming that makes it formalisable. `/opsp:propose` goes back to being purely the formalizer — writing the structured proposal with its driver-specs, decisions, milestones and bar.

The chain becomes symmetric, two think/persist pairs:

```
   explore  --think-->  backlog  --persist-->  initiative (O + G)
   triage   --think-->  propose  --persist-->  + DS · ADRs · milestones (S + M)
```

Triage's outcomes are: advance to propose, decline ([[DEC-035]]), or return for more exploration.

## Consideration Factors

| Factor | Weight | Triage as its own tool | Propose absorbs it |
|---|---|---|---|
| The lifecycle is self-explanatory | HIGH | Every phase is named ✓ | A phase exists but is invisible ✗ |
| Each tool does one thing | HIGH | Think, then persist ✓ | Brainstorm, classify and write ✗ |
| Symmetry with explore/backlog | MED | Exact ✓ | Asymmetric ✗ |
| Declining is a first-class outcome | MED | A triage outcome ✓ | Awkward inside a formalizer ✗ |
| Operator effort | LOW | One more invocation ✗ | Straight through ✓ |

## Rationale

The honest position is that `/opsp:propose` could absorb this and would behave acceptably. **The reason for a separate tool is explicitness, not capability** — the SDLC should be self-explanatory from its tool names, and a phase that exists in practice but has no name is a phase nobody reasons about.

Naming it also repairs `/opsp:propose`. Today it brainstorms, classifies and writes in one pass; afterwards it writes a structured proposal from material that is ready, which is a single job with a clear completion condition.

The resulting symmetry was not designed, which is the best evidence it is real: explore is to backlog as triage is to propose. Each pair separates thinking from persisting, and in both cases the persist step is where the operator commits.

Declining is the outcome that most needs somewhere to live. A formalizer rejecting its own input is strange; a triage step declining a candidate is exactly what triage means.

The cost is one more invocation on the direct path — which is why [[DEC-034]] keeps `explore -> propose` open for work that never rests in the backlog at all.

## Invalidation Trigger

If operators habitually run `/opsp:triage` and `/opsp:propose` back to back with nothing happening in between, the phase is not real and the two should merge. If triage grows artifacts of its own, it has become a second propose and the split is in the wrong place.
