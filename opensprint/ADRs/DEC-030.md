# DEC-030: Rebase, Attest, Archive, Merge — One PR, Gated on State Consistency

## Question

`/opsp:apply` currently ends by telling the operator to "merge the initiative branch to main when ready". That is where initiatives go dangling: a fully implemented PR merges, and the initiative is never attested or archived. When do those run, and what stops them being skipped?

## Decision

Four steps in order, on the initiative branch, in a **single** pull request:

```
  opsp/<initiative>  --rebase--*--attest--*--archive--*-->  main
```

1. **Rebase onto `main`** — so that compilation sees the record set the merge will actually produce.
2. **Attest** — posture, evidence, exposure, on the open PR ([[DS-CI-ATTESTATION]]).
3. **Archive** — which consumes compact ([[DEC-031]]) against the rebased record set.
4. **Merge.**

A pull request merging `opsp/*` into `main` is **gated on state consistency**: the initiative must be `attested` and the compiled views must be fresh. It is never gated on whether a bar was met.

A conflict in a derived artifact is resolved by **rebasing and recompiling**, never by hand-merging.

## Consideration Factors

| Factor | Weight | One PR, post-rebase | Closing PR after merge | Archive without rebase |
|---|---|---|---|---|
| Dangling is structurally impossible | HIGH | The gate prevents it ✓ | The second PR is optional in practice ✗ | ✓ |
| Derived artifacts are correct on `main` | HIGH | Compiled against real inputs ✓ | ✓ | Compiled against a stale record set ✗ |
| Commit history stays clean | HIGH | One PR ✓ | A PR containing only attestation ✗ | ✓ |
| Attestation gets reviewed | MED | In the PR ✓ | Its own review ✓ | ✓ |
| Branch must be current before closing | LOW | Required ✗ | Not required ✓ | Not required ✓ |

## Rationale

Compiling before the rebase is the decisive failure. A derived artifact built from the initiative branch's records does not include whatever else landed on `main` meanwhile, so it is wrong the instant it merges — and [[DEC-010]]'s `compact check` would be right to fail it. Rebasing first makes the input set the one the merge produces, and the output correct on arrival.

A closing pull request after the merge was rejected because it is the dangling problem with extra steps. Two pull requests means the second is optional in practice, which is exactly the failure this decision exists to remove — and a pull request whose only content is attestation adds noise to the history for no gain.

**The gate does not violate [[DEC-023]].** That decision forbids attest from judging whether a bar was met. Insisting that a bar was *answered* is a state-consistency check, the same category as `compact check` failing on drift. The tool may require an answer; it may never grade one.

Derived artifacts serialize concurrent initiative merges, and that is correct rather than unfortunate. Hand-merging a compiled file produces content no compile would ever generate — a direct [[DEC-006]] violation — so the only valid resolution is to rebase and recompile.

## Invalidation Trigger

If rebasing before close becomes routinely painful on long initiatives, the problem is initiative size, not this ordering. If the state gate blocks work that is genuinely ready, the state vocabulary is wrong — revisit [[DEC-024]], not the gate.
