# DEC-024: Initiative State Is Declared by the Tool and Checked by Code

## Question

[[DS-PROGRESSIVE-CRYSTALLIZATION]] gives an initiative a state that tracks how far down OGSM it has crystallized. Is that state derived from which cells are filled, declared in frontmatter, or both?

## Decision

**Declared by the tool, checked by code.** The frontmatter carries `state:`, written by whichever tool advanced the initiative. A deterministic check reports when the declared state disagrees with which cells are actually filled.

```
 state        what is settled                     written by
 -----------------------------------------------------------------
 exploring    Objective, Goal (forming)           /opsp:explore
 proposed     + Strategy, Measure (the bar)       /opsp:propose
 building     + milestones executing              /opsp:apply
 attested     + Posture, Evidence, Exposure       /opsp:attest
 completed    + compiled into the views           /opsp:archive
```

`abandoned` and `superseded` remain available to `/opsp:abandon`. The existing `status: completed` on archived initiatives maps to `state: completed`; `status` is retained so older initiatives still parse ([[DS-BACKWARD-COMPAT]]).

This requires the **first deterministic half for initiatives**. `decision-map.ts` parses driver-specs and decisions only; every reference to `initiatives/` in `src/` is skill prose.

## Consideration Factors

| Factor | Weight | Declared + checked | Fully derived | Declared only |
|---|---|---|---|---|
| Cannot drift silently | HIGH | The check reports disagreement ✓ | Cannot drift by construction ✓ | Drifts freely ✗ |
| Robust to partial records | HIGH | Declaration wins; check warns ✓ | Brittle — an unusual record misclassifies ✗ | Robust ✓ |
| Follows an established pattern | HIGH | The [[DEC-010]] manifest pattern ✓ | New ✗ | New ✗ |
| Explicit lookups over inference | HIGH | Explicit field ✓ | Inference from content shape ✗ | Explicit ✓ |
| Operator can correct it | MED | Yes ✓ | No — must change content ✗ | Yes ✓ |

## Rationale

This is exactly the shape [[DEC-010]] already solved. The manifest does not re-derive what a view contains; it records what the view was compiled from and fails when the two disagree. A declared state with a check over it is the same arrangement: a synthetic claim, gated deterministically.

Full derivation was tempting because it is drift-proof by construction, and was rejected on robustness. An initiative that legitimately has no Goal recorded, or whose milestones were delivered out of order, would be misclassified with no way for the operator to say otherwise. It also means inferring state from the *shape* of content, which is the pattern matching this codebase avoids.

Declaration alone is what the current `status` field already is, and the reason initiatives have no usable state today: nothing reads it, nothing checks it, and both existing initiatives carry `status: completed` with no record of how they got there.

The real cost is scope. Initiatives are the one artifact class with no code behind them, so this milestone builds a parser before it builds a state machine. That is also the prerequisite for the board ([[DEC-026]]) and for `mitigated-by` pointers to resolve ([[DS-FORWARD-CLOSURE]]).

## Invalidation Trigger

If the check never fires across many initiatives, declaration is reliable and the check is overhead. If it fires constantly, the state vocabulary does not match how work actually proceeds and the states themselves are wrong.
