# DEC-031: Archive Consumes Compact; Compact Stays Safe to Run Early

## Question

`/opsp:compact` and `/opsp:archive` are separate operator-invoked tools that both run at the end of an initiative. Is compact a step inside archive, a peer of it, or something the operator sequences by hand? And may compact run mid-initiative, against records whose work is unfinished?

## Decision

**Archive consumes compact.** Closing an initiative compiles the views as part of closing it; the operator does not run two tools in sequence and hope they remembered the second.

**Compact remains independently invocable, and running it mid-initiative is legitimate** — explicitly not constrained.

**Compact is not embedded in `/opsp:knockdown`.** Knockdown remains a separate, lengthy process whose output the operator must judge before compiling anything from it.

## Consideration Factors

| Factor | Weight | Archive consumes compact | Two separate steps | Compact also inside knockdown |
|---|---|---|---|---|
| Closing cannot half-happen | HIGH | One action ✓ | The second is forgettable ✗ | — |
| Compiles against complete records | HIGH | Every milestone is done by then ✓ | ✓ | Reverse-engineered, unjudged ✗ |
| Early compaction stays available | HIGH | Still invocable alone ✓ | ✓ | ✓ |
| Operator judgement preserved | MED | Archive is deliberate ✓ | ✓ | Compiles before the operator is satisfied ✗ |

## Rationale

The ideal that compact should not run against an in-flight initiative's records turns out to need no enforcement, because the lifecycle satisfies it: by the time archive runs, every milestone has merged, so there are no unfinished records to compile.

Early compaction is then safe for a reason that only became true with [[DEC-021]]. A mid-initiative compile renders decided-but-unattested claims as **decided**, not as fact — the third citation authority means the view cannot overstate what is known. So the productivity use is legitimate rather than tolerated, and constraining it would cost something and protect nothing.

The same reasoning describes knockdown precisely: a reverse-engineered surrogate is **entirely `observed`**, with nothing decided and nothing attested. That is an accurate account of what reverse-engineering produces rather than a defect. But whether the operator is satisfied with an inferred surrogate is a stochastic judgement, and judgement calls do not belong inside a compile — so knockdown ends, and the operator decides when to compact.

## Invalidation Trigger

If operators routinely run compact immediately after knockdown without reviewing in between, the review step is not real and embedding it would lose nothing. If archive-consuming-compact makes closing an initiative slow enough to defer, split them and solve forgetting with the state gate instead.
