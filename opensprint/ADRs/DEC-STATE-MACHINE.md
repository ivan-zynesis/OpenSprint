# DEC-STATE-MACHINE: Transitions Are Side Effects of Tools, and the Handoff Is a State

## Question

[[DEC-035]] named the initiative states and nothing moved between them.

Audited against the code rather than the intent: `/opsp:backlog` wrote `exploring` and `/opsp:triage` wrote `declined`. That was all. `/opsp:propose`'s frontmatter template **omitted the `state:` field entirely** — the word `proposed` appeared once, in a guardrail at the bottom of the file. Nothing wrote `building`, `attested` or `completed`. And `/opsp:archive` gated its merge on `state: attested`, a state no tool could produce, so the gate could never pass.

Every initiative in this project reached its state by hand-editing frontmatter.

Two questions fall out. Why did the prose fail, and is `building → attested` even the right shape?

## Decision

**Transitions are performed by a command, not described in prose.**

`opensprint advance <initiative> --to <state>` validates the move against an explicit table, writes the field, regenerates `BOARD.md`, and reports what the record now disagrees with. Every workflow calls it at its boundary. No workflow edits `state:`.

**A sixth state is inserted: `ready-for-attestation`.**

```
exploring ──propose──→ proposed ──apply starts──→ building
                                                     │  ↑
                                      apply ends     │  │ reexplore adds work
                                                     ↓  │
                                        ready-for-attestation
                                                     │
                                          attest ends│
                                                     ↓
                                                 attested ──archive ends──→ completed
     │                                                                          
     └──triage──→ declined ──triage──→ exploring
```

| From | To | By | When |
|---|---|---|---|
| exploring | proposed | `/opsp:propose` | the driver-specs, ADRs, milestones and bar are written |
| exploring | declined | `/opsp:triage` | the idea is dropped, with the reason recorded |
| declined | exploring | `/opsp:triage` | a declined idea is revived, keeping its history |
| proposed | building | `/opsp:apply` | the first milestone starts |
| building | ready-for-attestation | `/opsp:apply` | the last milestone closes — the dev hat is set down |
| ready-for-attestation | building | `/opsp:reexplore` | re-planning adds work that was not there |
| ready-for-attestation | attested | `/opsp:attest` | every bar carries a posture, and the change questions are answered |
| attested | completed | `/opsp:archive` | the views are compiled and the branch merges |

**Advancing records, it does not gate.** An illegal *move* is refused, because a state machine with no illegal moves is a text field. But a legal move into a state the content contradicts is written, with the contradiction reported beside it. Refusing there would turn a tool that records what happened into one that decides what may happen, which [[DS-SURROGATE-SCOPE]] puts outside this project.

## Consideration Factors

| | `advance` command | Prose instruction (status quo) | Inferred from content |
|---|---|---|---|
| Survives an agent that skips a step | ✓ — the step is a command, visibly absent from the transcript | ✗ — this is the observed failure | ✓ |
| Illegal moves refused | ✓ | ✗ | ✗ — nothing to refuse |
| Board stays current | ✓ — regenerated by the move | ✗ | ✓ |
| Operator can correct a wrong state | ✓ | ✓ | ✗ — the content *is* the state |
| Declining is expressible | ✓ | ✓ | ✗ — no content distinguishes it |

| | `ready-for-attestation` | `building → attested` direct |
|---|---|---|
| The handoff has a name | ✓ | ✗ |
| A board can show work waiting on a person | ✓ | ✗ — indistinguishable from work in progress |
| An author is stopped from attesting their own work | ✓ — the state says the hat changed | ✗ |
| States stay few | ✗ | ✓ |

## Rationale

**The prose failed because prose cannot be absent.** An instruction saying "now set `state: building`" produces nothing when skipped, and nothing looks exactly like nothing-to-do. A command produces a line in the transcript, a changed file and a regenerated board; its absence is visible. This is the same reasoning [[DEC-014]] applies to compiled artifacts — the difference between a step that was done and a step that was claimed is whether it left a trace.

That `/opsp:propose`'s template omitted the field is the sharpest evidence. The guardrail said to advance to `proposed`; the template an agent copies did not have the field to advance. Of the two, agents follow the template.

**The handoff needs a state because the hats are the same person.** [[DS-HATS-AS-CONTEXT]] says most hats are worn by one engineer. `building` says work is happening; `attested` says judgement happened. Between them is the moment the work stops being `dev`'s and becomes `product` and `maintainer`'s — and with no state for it, that moment is invisible, which means in practice it does not occur. The engineer finishes building and attests what they built.

[[DEC-043]] already refuses the authoring session. But a refusal needs something to fire on, and "the initiative was handed over, by whom, when" is the fact it needs. `ready-for-attestation` is that fact.

**It is also the only honest thing to put on a board.** A lead looking at `Doing` cannot tell work in progress from work waiting on somebody to put a different hat on. Those need different responses — one needs time, the other needs a person — so they are different columns.

**The backwards edge is the lifecycle, not an exception.** `ready-for-attestation → building` is how re-planning reopens work, and it is the same conversation [[DEC-039]]'s triage has before the work starts: an engineer and a product owner iterating on the plan. `/opsp:reexplore` is that conversation held again with the work in hand. Making the edge legal is what keeps the handoff a door rather than a cliff.

**`status` and `state` stay separate fields.** `status` is whether a record is live, which every record type has. `state` is where an initiative sits in its lifecycle, which only initiatives have. Collapsing them would put lifecycle vocabulary on driver-specs and ADRs, where it means nothing.

## Invalidation Trigger

If operators routinely run `advance` to a state the content contradicts and ignore the reported problems, then recording-not-gating is being read as permission rather than as trust, and the contradictions should block the move rather than accompany it.

If `ready-for-attestation` is routinely skipped — initiatives moving `building` → `attested` by hand because the handoff is to the same session anyway — then the state is documenting an intention nobody holds, and the honest fix is to make [[DEC-043]]'s refusal mechanical instead.
