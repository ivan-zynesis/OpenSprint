# DEC-009: Every Compiled Claim Carries Its Record Ids Inline

## Question

A compiled view is a synthesis. How does a reader — human or agent — get from a claim in the view to the record that justifies it, and how is a stale or incomplete synthesis caught?

## Decision

Every compiled claim carries its record ids inline, in the body text: "Production runs single-AZ at a 99% bar (`DEC-062`), with multi-AZ restored for the database (`DEC-064`)."

Dense inline citation is a requirement of the compiled format, not a nicety.

## Consideration Factors

| Factor | Weight | Inline citation | Citations in a trailer or manifest only |
|---|---|---|---|
| Drill-down path | HIGH | The id is at the point of need ✓ | Requires a lookup step ✗ |
| Catches missing amendments | HIGH | A claim citing only the superseded record is visibly incomplete ✓ | Invisible ✗ |
| Agent grounding | HIGH | The agent knows which record to read before acting ✓ | Must guess ✗ |
| Readability | LOW | Denser prose ✗ | Cleaner prose ✓ |

## Rationale

The load-bearing case is a partial supersession. Cashier's `DEC-064` ends one clause of `DEC-062` — a summary built from `DEC-062` alone states that production is single-AZ, which stopped being true on 2026-09-24. With inline citation, a section discussing availability that cites only `DEC-062` is visibly missing its amendment; without it, the error is silent.

This is also what makes the drill-down affordable under [[DS-SURROGATE-BUDGET]]. An agent orients on the view and reads the full record only for the decision it is about to act on — see [[DEC-015]].

## Invalidation Trigger

If citation density makes views materially harder for humans to read, a rendering that de-emphasises ids visually (rather than removing them) should be explored. Removing them invalidates the staleness argument entirely.
