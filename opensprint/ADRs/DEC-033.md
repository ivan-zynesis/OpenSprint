# DEC-033: Attest Loads the Bar and the Evidence — Never the Diff, the Design or the ADRs

## Question

[[DS-HATS-AS-CONTEXT]] says most hats are worn by the same engineer, so attestation is usually self-assessment. An agent or a person who just built the thing has every argument for why it works already in context. What stops attestation from being rationalisation?

## Decision

`/opsp:attest` runs on a **deliberately narrow context**:

```
  LOADS                               DOES NOT LOAD
  ------------------------------      -----------------------------
  initiative Objective + Goals        the implementation diff
  the bars (given / when / then)      the design discussion
  maintainer rows in scope            the ADR rationales
  CI evidence artifacts               the conversation that built it
```

If the evidence cannot answer the bar, that is a **finding about the evidence** — never a licence to go and read the code. The valid outcome is `posture: cannot assess — evidence inadequate`, with an exposure naming what is missing.

The skill must actively refuse to widen its own context, because an agent asked to attest will want to read the implementation.

## Consideration Factors

| Factor | Weight | Narrow context | Full context | Separate human reviewer |
|---|---|---|---|---|
| Adversarial distance | HIGH | Structural ✓ | None — rationalisation ✗ | Real ✓ |
| Works for a one-person squad | HIGH | Yes ✓ | Yes ✓ | Requires a second person ✗ |
| Creates pressure on CI | HIGH | Cannot route around weak evidence ✓ | Reads the code instead ✗ | Varies ✓ |
| Judges at the right altitude | HIGH | The bar is the contract ✓ | Drifts into reviewing mechanism ✗ | ✓ |
| Can diagnose a near-miss | LOW | No — reports and stops ✗ | Yes ✓ | Yes ✓ |

## Rationale

Excluding the ADR rationales is the part that feels wrong and is right. [[DS-STRATEGY-ALTITUDE]] already places attestation at the bar, not the mechanism; whether the implementation is well-reasoned is not the question being asked. **The bar is the contract.** Loading the rationale biases toward accepting, because a rationale is an argument for the thing that was built.

This rule and [[DS-CI-ATTESTATION]]'s bet are the same mechanism, not two ideas. If the attester may not read the code, weak evidence **cannot** be worked around — the only way to attest is to make the pipeline produce something sufficient. One rule, enforced in one place, creates the pressure.

It is also self-correcting. `cannot assess` does not block ([[DEC-023]]) and produces an exposure naming the missing coverage, which becomes a backlog item that makes the next attestation possible. The system emits its own instructions for becoming attestable.

The real cost: an attester who cannot diagnose a near-miss. Told a bar was not met, it cannot say why, because that would require the code. That is accepted — diagnosis is the dev hat's work, and mixing the two is exactly what this decision prevents.

## Invalidation Trigger

If `cannot assess` is the outcome on most bars for a long stretch, the pipeline is the bottleneck and that is the finding working as designed — not a reason to widen the context. If attesters routinely need one specific excluded artifact, name and add that artifact rather than relaxing the rule.
