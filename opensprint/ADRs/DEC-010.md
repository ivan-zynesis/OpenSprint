# DEC-010: Two-State Provenance Manifest, Enforced by `--check`

## Question

How does the system know a compiled view is current, and how is a stale view prevented from being trusted?

## Decision

`compact` maintains a provenance manifest recording, per hat and per section, the record ids and content hashes that section was compiled from, plus a hash of the rendered output.

Because [[DEC-006]] makes views read-only, there are two states:

| Condition | State | Response |
|---|---|---|
| Input hashes changed | **stale** | Recompile that section from its full inputs |
| Output hash changed | **tampered** | Fail: the edit will be lost — if the view is wrong, the system is wrong, so run `/opsp:explore` |

`opensprint compact --check` is deterministic and fails CI on anything that is not fresh.

## Consideration Factors

| Factor | Weight | Content-hash manifest | Git SHA watermark |
|---|---|---|---|
| Survives squash-merge | HIGH | Unaffected ✓ | The recorded SHA becomes unreachable ✗ |
| Works in shallow CI clones | HIGH | No history needed ✓ | Cannot resolve the SHA ✗ |
| Cross-universe ([[DEC-001]] worktrees) | HIGH | Hashes travel with content ✓ | SHAs diverge per branch ✗ |
| Granularity | MED | Per section — recompile only what moved ✓ | Whole-file only ✗ |

## Rationale

This is [[DS-LOOP-CLOSURE]] applied to the surrogate itself. A view cannot quietly disagree with its driver-specs and ADRs, whether the records moved or the view did. Drift in the compacted layer becomes a build failure, which is the standard the rest of the loop is held to.

It does not conflict with the archive specification's "SHALL NOT version — ADRs are the version history". The manifest records *where a view came from*; git still holds the history.

## Invalidation Trigger

If per-section hashing proves too granular to maintain — sections renamed or merged often enough that the manifest churns — per-hat hashing is the fallback, at the cost of recompiling more than necessary.
