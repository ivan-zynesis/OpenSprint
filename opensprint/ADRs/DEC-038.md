# DEC-038: A Bar Is Written in BDD Form, Split by Hat

## Question

[[DEC-019]] gives a measure a `### Bar` block, and [[DS-CI-ATTESTATION]] requires a bar to be assessable from pipeline output. Free prose satisfies neither. What form does a bar take?

## Decision

BDD, in one of two forms chosen by hat:

**Product** — a user story:
```
  as a   <persona>
  I want <goal>
  for    <reason>
```

**Maintainer** — given / when / then:
```
  given  a credential is committed
  when   CI runs
  then   the build fails
```

Everything else in the measure anatomy — posture, evidence, exposure — stays simple qualitative description. The structure is spent where it buys something.

## Consideration Factors

| Factor | Weight | BDD, split by hat | One form for both | Free prose |
|---|---|---|---|---|
| A pipeline can be pointed at it | HIGH | given/when/then maps to a test ✓ | Partially ✓ | No ✗ |
| Natural for the hat that writes it | HIGH | Each hat gets its idiom ✓ | One hat writes awkwardly ✗ | ✓ |
| Attestable from evidence alone | HIGH | The bar states its own check ✓ | ✓ | Requires interpretation ✗ |
| Non-engineer can read it | HIGH | Both forms are plain language ✓ | ✓ | ✓ |
| Vocabulary to learn | LOW | Two forms ✗ | One ✓ | None ✓ |

## Rationale

The split is not a preference, it is what the hats actually produce. A maintainer bar written as a user story becomes an awkward fiction — *"as a maintainer, I want credentials not to be committed"* says less than *"given a credential is committed, when CI runs, then the build fails"*, and only the second tells you what to point a pipeline at. Product bars invert it: a user story carries the persona and the reason, which given/when/then has nowhere to put.

BDD is what makes [[DS-CI-ATTESTATION]] mechanically possible. A bar in given/when/then form **is already a test specification**, so the gap between stating a bar and producing evidence for it is as small as it can be — and an engineer writing the bar can see immediately whether CI could ever answer it.

Keeping posture, evidence and exposure as prose is deliberate. Those are judgements and references, and imposing structure on them would produce filled-in templates rather than thought. [[DS-MEASURE-ANATOMY]] already names the parts; naming is structure enough.

## Invalidation Trigger

If product bars are routinely written in given/when/then because the author finds it easier, the hat split is theoretical and one form will do. If bars are written in BDD and still cannot be attested from CI output, the problem is the pipeline, not the form.
