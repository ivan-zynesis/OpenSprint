# DEC-012: Explicit Primary-Hat Field; the Hat Set Is a Per-Project Registry

## Question

How does `compact` know which hat a driver-spec or ADR belongs to, and is the hat set fixed?

## Decision

Every driver-spec and ADR carries an explicit `hat` field naming its **primary** hat. One hat per record — cross-references come from the dependency graph, not from multi-tagging.

The valid hat set is a per-project registry, defaulting to `product`, `maintainer`, `dev`, `devops`, plus `agreements` for cross-hat constraints. Validation is an explicit list lookup against the registry.

Existing records are backfilled on first compile, defaulted from the driver-spec `type` where that type maps cleanly, with owner confirmation batched by area.

## Consideration Factors

| Factor | Weight | Explicit field | Inferred from `type` or content |
|---|---|---|---|
| Works on real data | HIGH | Deterministic ✓ | cashier sets `type: driver-spec` on all 17 driver-specs and `type: adr` on all 64 ADRs — nothing to route on ✗ |
| Stability | HIGH | Changes only when someone changes it ✓ | Re-inference could silently re-file a record ✗ |
| Per-project flexibility | MED | The registry is configuration ✓ | A fixed taxonomy ✗ |

## Rationale

The existing `type` field cannot carry this. Across four projects it means four different things: cashier uses a single constant, pixlr-web invented `operating-model`, and no project tags ADRs by domain at all. Routing needs a field whose meaning is fixed by the tool.

One hat per record, rather than multi-tagging, keeps the partition a genuine partition. A record appearing under several hats has no single owner, which defeats [[DS-SME-OWNERSHIP]]. Where product needs to see a dev decision, the graph provides it: product's view says a constraint is answered by some decision, and dev's view holds that decision in full.

The registry is per-project because [[DS-SQUAD-HATS]] makes the hat set a property of the product — a back-office system needs no designer hat, a consumer product does.

## Invalidation Trigger

If records routinely and genuinely belong to two hats, a secondary hat field may be warranted — but only if ownership stays singular, because a record with two owners has none.
