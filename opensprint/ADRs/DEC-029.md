# DEC-029: Planning Happens in the Initiative's Worktree; the Planning Tools Create It

## Question

[[DEC-001]] puts `opensprint/` in the branch, so it travels with the code. Backlog items and proposals are records with no code at all. Where are they authored — on `main`, or in the initiative's own worktree?

## Decision

**In the initiative's worktree.** `/opsp:backlog`, `/opsp:triage` and `/opsp:propose` **create or switch to the correct worktree if they are not already in one**, rather than assuming the operator did it. The worktree exists from the first persisted thought, not from `/opsp:apply`.

An initiative therefore lives entirely in one branch from birth, and reaches `main` exactly once — through the single pull request described by [[DS-SURROGATE-GIT-CONTRACT]].

## Consideration Factors

| Factor | Weight | Worktree from backlog | Planning on `main` |
|---|---|---|---|
| Planning is visible to the work it plans | HIGH | Records are on the branch that implements them ✓ | Uncommitted on `main` — invisible to the worktree ✗ |
| No direct commits to `main` | HIGH | Everything arrives by PR ✓ | Planning bypasses review entirely ✗ |
| Uniform with [[DEC-001]] | HIGH | `opensprint/` always travels with its branch ✓ | Records appear on `main` ahead of their branch ✗ |
| Operator does not manage worktrees by hand | HIGH | The tools do it ✓ | Nothing to manage ✓ |
| A backlog is readable in one place | HIGH | **No — scattered across branches** ✗ | Yes ✓ |
| Record-id collisions | MED | Every initiative can collide ✗ | Only from `apply` worktrees ✓ |

## Rationale

The earlier version of this decision put planning on `main`, and practice refuted it within the hour. `/opsp:apply` created a worktree from `main`'s last commit, and the thirty-four planning records for this very initiative were **uncommitted on `main`** — so the worktree meant to implement them could not see them. The only two ways out were committing planning directly to `main`, which bypasses review entirely, or carrying uncommitted work across worktrees by hand. Neither is a contract.

Making the planning tools responsible for the worktree is what removes the failure rather than relocating it. The operator never has to know which worktree they should be in; `/opsp:backlog` on a fresh idea creates `opsp/<initiative>` and writes there, and `/opsp:propose` on an existing backlog item switches to the branch that already holds it. An initiative is then one branch from first thought to merge, which is also the simplest thing to explain.

**The cost is real and is not solved.** The previous version's decisive argument — *a backlog nobody can see is not a backlog* — still stands, and this decision does not answer it. Backlog items now live on branches, so the compiled board shows only what the current branch knows, and the one interaction [[DS-HATS-AS-CONTEXT]] grants a non-technical stakeholder depends on reading all candidates in one place. Cross-branch listing was previously deferred as narrow; it is no longer narrow, and `sdlc-operating-contract` records it as blocking that path rather than as a convenience.

Record-id collisions also widen back out, which is precisely what [[DEC-036]] exists to make impossible by construction.

## Invalidation Trigger

If cross-branch listing proves unsolvable at acceptable cost, the backlog — and only the backlog — may have to live on `main` while proposals stay on branches, splitting this decision in two. The first sign is a stakeholder unable to see candidate work without being walked through the forge.
