# DEC-043: The Agent That Wrote the Tests May Not Attest Them

## Question

[[DEC-040]] puts test files in the attester's context. The agent that wrote those tests is usually
the one available to attest. Does the existing "refuse to continue in the authoring session" rule
still cover this?

## Decision

No — it is widened and hardened. `/opsp:attest` refuses when the session **authored the
implementation or its tests**, not merely when it authored the implementation.

The refusal is explicit, stated first in the instructions, and not satisfiable by the agent
asserting it has set the context aside. A fresh session is required.

Where the operator attests manually, the same rule is stated as guidance: whoever wrote the tests
should not be the one judging whether they assert the bar.

## Consideration Factors

| Factor | Weight | Refuse on tests too | Refuse only on implementation | Trust the narrow context |
|---|---|---|---|---|
| Resists rationalisation | HIGH | The author cannot grade their own assertion ✓ | Test author attests their own tests ✗ | ✗ |
| Honest about what changed | HIGH | [[DEC-040]] added the risk; this answers it ✓ | Pretends the risk did not move ✗ | ✗ |
| Workable for one person | MED | Needs a second session, not a second person ✓ | ✓ | ✓ |
| Enforceable | LOW | By instruction only ✗ | ✗ | ✗ |

## Rationale

[[DEC-033]] excluded the implementation precisely because an agent holding it rationalises.
[[DEC-040]] then let the tests back in — which is correct on altitude grounds, and which **moves the
risk rather than removing it**. The question "does this test assert the bar?" is falsifiable, but not
by the person who wrote the test believing it does.

[[DS-HATS-AS-CONTEXT]] already makes the point that a hat is what you load, and that a narrow context
arrived at by forgetting is not a narrow context. Writing the tests *is* holding the context. So the
existing refusal was always about authorship rather than about which file was open, and this states
it that way.

**The cost is one extra session, not one extra person.** That matters: this tool is built for teams
where one engineer wears every hat, and a rule requiring a second human would simply be ignored.

Enforcement is by instruction, which is weak and acknowledged. Code cannot see what a session wrote.
What code *can* do is make the written output checkable — which is [[DEC-027]]'s bound, unchanged.

## Invalidation Trigger

If operators routinely attest in the authoring session anyway, the rule is theatre and the honest
response is to remove it and record that attestation here is self-assessment — not to keep an
instruction nobody follows.
