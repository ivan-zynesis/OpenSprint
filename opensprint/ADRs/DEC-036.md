# DEC-036: Decisions Are Named Semantically; Initiatives Are Named Chronologically

## Question

Driver-specs use semantic ids (`DS-BACKWARD-COMPAT`); changes use semantic directory names; decisions use incrementing numbers that collide when two worktrees allocate the same one ([[DS-PARALLEL-EXEC]]). Replacing the number loses the chronological ordering `ls` currently gives. Does that ordering matter, and where?

## Decision

**It matters for initiatives and not for decisions**, so the two artifact classes are named differently.

**Decisions — pure semantic ids, no date, no number:**

```
  filename   DEC-ATTEST-NOT-COMPACT.md
  id:        DEC-ATTEST-NOT-COMPACT
  citation   [[DEC-ATTEST-NOT-COMPACT]]
```

**Initiatives — a date prefix on the filename, id unchanged:**

```
  filename   20261009-lifecycle-beyond-build.md
  id:        lifecycle-beyond-build
```

**Nothing existing is renamed.** `DEC-001` through `DEC-039` keep their numbers permanently; the tool stops allocating new ones. Existing initiative files may be prefixed, because their `id:` does not change and nothing cites a filename.

**Two prerequisites, each blocking its own half:**

| Change | Blocked on | Because |
|---|---|---|
| semantic decision ids | widening `RECORD_ID_PATTERN` in `src/core/compact/rules.ts` | it matches `DEC-\d{3}`, so a semantic id is invisible to the rule harvest — reported `decision-unguarded` forever and missed by `rule-guards-dead-record` |
| date-prefixed initiatives | the `initiative-parser` milestone | skills construct `initiatives/<name>.md` directly; resolution must move to frontmatter `id:` |

## Consideration Factors

| Factor | Weight | Semantic for DEC, dated for initiatives | Dated for both | Numbers everywhere |
|---|---|---|---|---|
| Collision-free across worktrees | HIGH | Both classes ✓ | Both ✓ | Collides ✗ |
| Ordering where it means something | HIGH | Journey for initiatives, tree for decisions ✓ | Dates on nodes that are not sequential ✗ | Numbers that cluster by initiative, not by thought ✗ |
| Citations are self-describing | HIGH | `[[DEC-ATTEST-NOT-COMPACT]]` reads ✓ | ✓ | `[[DEC-014]]` says nothing ✗ |
| A record is findable from its id | HIGH | filename contains the id ✓ | Date prefix must be known or globbed ✗ | ✓ |
| Topic clustering in `ls` | MED | Alphabetical groups `DEC-ATTEST-*` ✓ | Scattered by date ✗ | Scattered ✗ |
| Ids are stable forever | HIGH | Never reassigned ✓ | ✓ | ✓ |

## Rationale

**A decision has no meaningful chronology.** It is a node in a hierarchy, and its position is given by `depends-on`, `depth` and its place in `DECISION-MAP.md` — not by when it was written. It is also bound to the initiative that produced it, which supplies the only grouping a reader actually uses. The existing numbers never delivered chronology anyway: `DEC-018` through `DEC-028` were all written in one sitting, `DEC-029` through `DEC-039` in another, so they cluster by initiative while appearing to encode sequence.

Dropping the number entirely then costs nothing and buys two things. Collisions become impossible by construction — and if two worktrees independently coin the same slug, they have found the same decision, which is information rather than a conflict. And alphabetical order starts grouping by topic, which is how a decision corpus is actually read: `DEC-ATTEST-CONTEXT-NARROW`, `DEC-ATTEST-NEVER-GATES`, `DEC-ATTEST-NOT-COMPACT` land together.

**An initiative is a chronological journey the team walked**, which is exactly what a date prefix records. [[DS-PROGRESSIVE-CRYSTALLIZATION]] makes an initiative a container that fills over time, and a backlog item's prefix is its birth date — the moment the idea arrived. Reading `initiatives/` in order is reading the project's history, which reading `ADRs/` in order is not.

This works at all only because **filename and id are already decoupled in code**: both readers in `decision-map.ts` take `id` from frontmatter and use the filename solely to filter `.md` and to sort. The coupling was pure convention. That decoupling also makes the choice reversible — nothing cites a filename, so a future change of ordering scheme is a rename loop rather than a rewrite of every compiled citation.

Keeping the full id inside the decision filename is deliberate: `DEC-ATTEST-NOT-COMPACT` must be findable without a grep, which a bare slug or a date-prefixed name would cost.

## Invalidation Trigger

If semantic ids are routinely coined too specifically to survive the decision being superseded, the naming needs conventions, not a different scheme. If reading `initiatives/` chronologically turns out never to happen, drop the prefix — it is a filename, so nothing breaks.
