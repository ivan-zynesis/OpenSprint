# DEC-020: A Maintainer Strategy Cites Its Implementers; the Existing Citation Rule Enforces the Altitude

## Question

[[DS-STRATEGY-ALTITUDE]] requires maintainer strategies to stay above domain know-how. Rendering is the synthetic half of compact — nothing mechanical stops a skill writing `"we use Argon2id with a 64MB memory cost"` into a strategy cell. How is the altitude enforced?

## Decision

A maintainer strategy cell renders the **position plus a pointer** to the `dev` or `devops` decisions that implement it, traversing the existing `depends-on` graph. It never renders the mechanism.

No new enforcement mechanism is added. [[DEC-009]] already requires every compiled claim to cite a record id or a path, and know-how written into a maintainer strategy has no maintainer record to cite — so it cannot be written without breaking a rule that already exists.

One new harvest rule: `strategy-unimplemented` — a maintainer strategy with no `dev`/`devops` decision descending from it.

## Consideration Factors

| Factor | Weight | Citation rule enforces it | A length or vocabulary rule | Unenforced convention |
|---|---|---|---|---|
| New mechanism required | HIGH | None ✓ | A heuristic on prose ✗ | None ✓ |
| Catches the actual failure | HIGH | Uncitable claim cannot be written ✓ | Crude; misses short know-how ✗ | Nothing catches it ✗ |
| Pattern matching avoided | HIGH | Graph traversal, not regex ✓ | Keyword or length matching ✗ | — |
| Surfaces the inverse gap | MED | `strategy-unimplemented` ✓ | No ✗ | No ✗ |
| Depends on compact's synthetic half behaving | LOW | Still partly ✗ | Mechanical ✓ | Fully ✗ |

## Rationale

The altitude rule looked like it needed a new guard and does not. The constraint that a compiled claim must cite its source turns out to be load-bearing in a second way: it bounds not only *whether* a claim is true but *which hat may make it*. A mechanism detail belongs to a `dev` record, so stating it in a maintainer view would require citing a record the maintainer hat does not own.

The pointer direction matters. The maintainer view becomes an **index into** `dev` and `devops` rather than a competing description of the same system — which is [[DS-BIG-PICTURE]] applied across hats, and which removes the drift risk entirely, since there is only ever one description of a mechanism.

`strategy-unimplemented` is the more valuable half in practice. A stated maintainer strategy with nothing descending from it is intent nobody built, and today it is invisible: the harvest only reports constraints nothing *answers*, which a strategy with a child decision satisfies even when that decision implements something else.

`squad/product.md` currently files *"this hat states intent and another hat answers it; every ADR routes to dev"* as a structural finding. This decision reclassifies that as the intended topology.

## Invalidation Trigger

If maintainer strategies routinely have no implementing decision because the mechanism is genuinely absent rather than unrecorded, `strategy-unimplemented` is reporting a planning gap rather than a documentation gap, and belongs on the roadmap instead of in open loops.
