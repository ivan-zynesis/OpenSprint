# DEC-018: The Six Objectives Are Maintainer's Shipped Section List, Selected by an `objective` Field

## Question

[[DS-MAINTAINER-INHERITED]] establishes seven objectives for the `maintainer` hat. How are they represented — as records the operator writes, as a new classification axis, or as part of the hat's shape?

## Decision

The seven are the **default section list for the `maintainer` hat**, shipped in `DEFAULT_SECTIONS_BY_HAT`. An operator never writes an objective record for this hat.

Records carry `role: goal | strategy` and a new optional `objective:` field naming which of the seven they serve. A section selects on `objective` exactly as it selects on `roles` today.

`role` widens to accept a string or a list, normalised to a list — the same treatment [[DEC-016]] gave `hats`. A record stating both a goal and its strategy declares both.

The list is **extensible**: a project declaring its own sections may add to it. `maintainer` also gains default roles, which it currently lacks.

## Consideration Factors

| Factor | Weight | Shipped section list | Objectives as `goal` records | Orthogonal `domain` field |
|---|---|---|---|---|
| Inherited, not authored | HIGH | The tool supplies them ✓ | Every project rewrites the same seven ✗ | Supplied, but as a label not a shape ✓ |
| Empty objective is visible | HIGH | Renders as an empty row ✓ | Absent record renders nothing ✗ | Absent group renders nothing ✗ |
| New mechanism required | HIGH | None — this is what a section list is ✓ | None ✓ | A second classification axis ✗ |
| OGSM semantics preserved | MED | Objective is a shape, goal is a record ✓ | A domain is not a quantified outcome ✗ | Preserved ✓ |
| Operator friction at write time | MED | One field: `objective` ✓ | None ✓ | Two axes to fill ✗ |
| Tool asserts universal content | LOW | Yes — a departure ✗ | No ✓ | Yes ✗ |

## Rationale

The decisive argument is that an objective with nothing recorded against it must still appear. `cost & budget` with an empty row is the single most useful cell in the view — it says nobody has stated what this system costs to run. A representation where an absent record means an absent heading cannot say that, which rules out both alternatives.

Representing the seven as sections turns out to need **no new mechanism at all**. `DEFAULT_SECTIONS_BY_HAT` already ships a fixed, project-overridable shape per hat; `maintainer` already had one (`bars · posture · evidence · exposure`), authored by hand into this repository's config. This replaces that list. The only addition is `objective` as a second selector beside `roles`, which mirrors machinery that exists.

Widening `role` to a list is additive and therefore safe under [[DS-BACKWARD-COMPAT]]: a record written as `role: strategy` still parses. [[DEC-016]] already set the precedent and the normalisation helper.

The real cost is recorded honestly: this is the **first time the tool asserts universal content rather than universal structure**. [[DS-SQUAD-HATS]] makes the hat set a project's own; seven named domains is the tool claiming to know what every software project worries about. Keeping the list extensible is what makes the claim falsifiable rather than baked in — a consumer product needing `accessibility` adds a row in config rather than forking.

That extensibility has already proved its worth. `availability & continuity` was declined twice during exploration and then added on review, once it was checked against the others and found genuinely uncovered. The list is expected to move again.

## Invalidation Trigger

If a project records a maintainer bar that fits none of the seven without strain, the list is wrong — add the row rather than forcing the record. If projects routinely add the *same* extra row, it belongs in the shipped default and [[DS-MAINTAINER-INHERITED]] should be revised.
