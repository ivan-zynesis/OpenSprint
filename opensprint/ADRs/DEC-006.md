# DEC-006: Hat Views Are Compiled Artifacts, Never Hand-Edited

## Question

The compacted per-hat surrogate is meant to be managed by the human with the subject-matter expertise for that hat. Does "managed by" mean the owner edits the file, and if so, how do edits get back into the driver-specs and ADRs the file was compiled from?

## Decision

Hat views are compiled artifacts. They are not editable by hand — not the compiled body, and not the charter (see [[DEC-008]]).

The view honestly shows the current state of the system. When a flaw is found in a view, the flaw is in the system, not in the document. The fix path is to start a new `/opsp:explore`, which feeds `/opsp:propose` — see [[DEC-007]].

## Consideration Factors

| Factor | Weight | Read-only views | Editable views with write-back |
|---|---|---|---|
| Attribution of an edit | HIGH | No edits to attribute ✓ | A compiled section synthesises many records; an edit to one sentence has no unambiguous home ✗ |
| Risk to the record | HIGH | compact never writes a driver-spec or ADR ✓ | A misclassified edit silently rewrites the source of truth ✗ |
| Recoverability | HIGH | Every view regenerates from the record ✓ | An overwritten record is recoverable only from git ✗ |
| SME ergonomics | MED | The owner reviews and triages rather than authors ✓ | The owner writes in their own file ✓ |
| Machinery required | MED | A compiler ✓ | A compiler, a classifier, a confirmation loop, a four-state manifest ✗ |

## Rationale

The whole point of the surrogate is that the driver-specs and ADRs are the source of truth. A view that can be edited becomes a second source of truth the moment someone edits it, and the next compile either destroys their work or defers to it. Neither outcome is acceptable.

Making the view strictly derived keeps one honest invariant: **if the document is wrong, the system is wrong.** That converts every documentation defect into a real engineering backlog item instead of a writing task.

It also collapses the blast radius of compaction. Because compact never mutates the record and every view is regenerable, it cannot corrupt the surrogate the way [[DEC-002]] guards against for reconciliation. compact therefore does not need the operator-only guardrail that `/opsp:rebase` and `/opsp:abandon` carry under [[DS-HIGH-IMPACT-OPS]].

## Invalidation Trigger

If owners in practice route around the read-only rule — editing views anyway and losing work at the next compile — the friction is real and the constraint should be revisited. The likely answer then is a narrower authored region with mandatory inline citation ([[DEC-009]]) to make attribution tractable, not free-form editing.
