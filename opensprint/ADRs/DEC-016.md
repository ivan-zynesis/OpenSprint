# DEC-016: A Record Declares One or More Hats; There Is No `agreements` Hat

## Question

[[DEC-012]] fixed exactly one hat per record and added a fifth `agreements` hat to hold constraints that cross hats. Applied to this repository's own records, six of twenty-one landed in `agreements`. Is one-hat-plus-a-bucket the right model?

## Decision

A record declares **one or more** hats. The `agreements` hat is removed; the default set is `product`, `maintainer`, `dev`, `devops`.

A constraint that matters to two hats is listed under both and appears in both compiled views.

The frontmatter key is `hats`. It accepts a bare string or a list, normalised to a list: `hats: product` and `hats: [product, maintainer]` are both valid.

## Consideration Factors

| Factor | Weight | Multi-hat, four hats | One hat plus `agreements` |
|---|---|---|---|
| Maps to real accountability | HIGH | Every hat names someone answerable ✓ | `agreements` names no one; it is a document category wearing a hat's clothes ✗ |
| Fidelity to the model | HIGH | The source model has four hats ✓ | Invents a fifth the model does not have ✗ |
| Cross-cutting constraints | HIGH | Appear in every view that needs them ✓ | Exiled to a file neither owner reads first ✗ |
| Review routing | MED | A cross-cutting record crosses both desks ✓ | Crosses a desk belonging to nobody ✗ |
| Partition cleanliness | LOW | A record can appear twice ✗ | Each record appears once ✓ |

## Rationale

`agreements` was a workaround for the single-hat rule, not a hat. Nobody is the agreements owner, which is precisely what [[DS-SME-OWNERSHIP]] requires a hat to have. Six of twenty-one records routing there was the signal that the rule, not the records, was wrong.

The original objection to multi-tagging was that a record with two owners has none. That conflated two things. Ownership attaches to the **hat file** — its reviewer, its escalation target, its backlog. A record appearing in two views is reviewed by both owners, which for a genuinely cross-cutting constraint is the correct outcome rather than a failure of the partition.

The cost is real but small: the same record renders in more than one view, so a reader of two views sees it twice. That is cheaper than a fifth file nobody owns.

## Invalidation Trigger

If records routinely carry three or more hats, the hat set is too fine-grained for the project and the registry should be reconsidered — not the multi-hat rule.
