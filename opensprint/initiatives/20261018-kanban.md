## Description

**Objective.** Initiative management that every agent and every human sees as one live state, no
matter which worktree, branch or pull request the work currently sits in — and that holds up at the
scale of a large, fast-moving monorepo.

**Goal.** In-flight initiative state lives in a single central store — on `origin/main`, or on a
dedicated `origin/kanban` — read and written only through the `opensprint` tool. A completed
initiative needs only a static record. Any agent or human can stand the live board up in their own
browser, through a skill that fetches the board data and renders it as HTML. An adopter can be
onboarded in one simple step. You could tell this had landed when two people on different branches
see the same board, and the same claim, without either of them fetching the other's branch.

**What prompted it.** Raised by Ivan Lee at the archive of `board-owners`. The compiled board is
still an instantaneous state: it is compiled from the latest known state of every recorded backlog
item and initiative, and `compact board --all-branches` makes "latest known" depend on what this
machine has fetched. The tool is gaining tracker capability — Jira's in all but name — which is not
wrong in itself, but sits awkwardly while the backlog lives in different worktrees, on different
branches, in different pull requests on the remote.

Moving the backlog onto `main` or a dedicated branch is hard to enforce: it depends on each adopter's
own discipline to keep that branch for initiative management alone, and OpenSprint cannot control a
downstream team's git workflow. None of this is critical at this project's size; it becomes critical
in the largest, fastest monorepos, where centralised version control — a single central copy of
`main` — is the inspiration, and suggests a centralised model may be the right one for the board.

It would revisit `DEC-026` (the board is compiled), `DEC-BOARD-ALL-BRANCHES` (printed on demand,
never committed) and `DEC-029`, whose Invalidation Trigger already names the backlog-on-`main` split.
An early proof of concept — the board as a remote store — is to be tried on branch `opsp/kanban`.

**Who the board is for.** Much of OpenSprint's progress is meant to keep an agent in the loop at
least, and often the agent is its primary consumer. So everything on the kanban is a
**visualisation**: it is for humans to use, and for us to understand the tool. Under the hood an agent
does not read the page or click its buttons — it works through the `opensprint` CLI. The board shows
what the CLI's state already says, and its buttons only hand a human the command that starts an agent
on the next step.

## Strategy

Keep in-flight state on one remote branch, `origin/kanban`, as one plain-text card per initiative,
read and rendered with nothing but git, the installed skill and a static HTML template; and move
cards only through the opensprint command that enforces the state machine. Each column is a stage
with one workflow: forward continues it, backward escalates up the hat ladder. A button copies the
command that starts a fresh agent session in the card's worktree. Clicking into an initiative shows
its milestones as tickets, in columns that follow the opsx cycle.

Proven feasible in a proof of concept on `opsp/kanban`: the store, the read and render playbooks,
the template, and the continue / escalate buttons with their launch command, rendered live from
`origin/kanban`.

## OPSX Changes

- `board-store` — archived as `openspec/changes/archive/2026-10-27-board-store/`; new capability
  `opsp-live-board`. `src/core/kanban.ts` names the layout and the card format, and holds the one
  write path: read without a checkout, commit through a temporary index, fast-forward push, re-read
  and re-apply on a lost race. `opensprint kanban init` creates and seeds the board in one commit, and
  `opensprint kanban seed` adds missing cards and reports drift, with `--resync` to rewrite it. A card now
  carries each milestone with its stage, which `milestone-board` renders. Learned: a lost race is told
  apart from a failed push by asking the remote where the board is, not by parsing git's message.
- `board-skill-template` — archived as `openspec/changes/archive/2026-10-27-board-skill-template/`;
  new capability `opsp-kanban-skill`. `/opsp:kanban` (skill `opensprint-kanban`) lists the board and
  renders it with git and a shell. Its page is the package asset `assets/kanban/board.html`, which
  loads nothing, takes its columns from `KANBAN_COLUMNS` at generation, and shows each card's milestone
  progress. Learned: **`opensprint update` had never written the opsp layer.** `writeOpspLayer` now
  writes it for `init` and both of `update`'s paths, and writes the template in every delivery mode.
  This repository's own kanban skill is now generated; its other generated `.claude/` files are still
  older than their templates, left for the next `update` here.
- `stage-actions` — archived as `openspec/changes/archive/2026-10-27-stage-actions/`. A card's
  moves are read off `TRANSITIONS`. Continue is the transition to a later state, never into
  `declined`; escalations are the transitions back; Backlog's continue is triage's pick-up, the one
  move that is not a transition. A button copies a launch script: find or add the card's worktree,
  then start a fresh session. `ToolCommandAdapter` gains optional `commandReference` and
  `sessionLauncher`, which only Claude Code fills; every other tool gets a prompt naming the skill.
  Verified by clicking a button headlessly and running the copied script against a scratch remote.
  Learned: where the ADR's prose and the transition table differ — repropose and reexplore listed for
  the whole Dev and Attestation columns, which `proposed` and `attested` do not allow — the board
  follows the table.
- `workflow-moves-card` — archived as `openspec/changes/archive/2026-10-27-workflow-moves-card/`.
  `opensprint advance` moves the card after the file, and validates the card's own move: a missing
  card is created, a drifted card is left alone and reported. `opensprint claim` claims the card
  before the file, so the remote arbitrates, and refuses a card someone else holds unless
  `--take-over`. A real lost race, staged with a `pre-push` hook, is tested to end in a refusal and
  not an overwrite. The board never blocks a move, and `--no-board` skips it. Learned: **triage
  declined by telling the agent to write `state: declined` by hand**, the last move left to prose;
  it now runs `advance`. Backlog runs `opensprint kanban seed <id>`, and `--remote` is gone, so
  `origin/kanban` is the only board any command or playbook touches.
- `resumable-workflows` — archived as `openspec/changes/archive/2026-10-27-resumable-workflows/`.
  Triage, propose and attest each check their state first, and stop where their move has already
  happened. Triage writes its thinking to `## Triage` (Weighed · Leaning · Open) before it stops, and
  resumes from it. Propose reads that section in place of a conversation, treats listed records on
  disk as confirmed, and writes only what is missing. Attest finds this pass with `git log -S` on
  the handoff, skips the bars judged since, and still confirms the frame in every session. Learned:
  propose's instructions expected "the strategy that triage worked out" to arrive by conversation,
  which a fresh session started from the board never has.
- `milestone-board` — archived as `openspec/changes/archive/2026-10-27-milestone-board/`. Milestone
  stages move through an explicit table, `MILESTONE_STAGE_MOVES`: forward through the opsx cycle, and
  back from Review only, as a change request. `opensprint kanban stage` writes each move, and refuses
  one out of order or a `done` the file has not checked. Apply calls it at every step of the cycle.
  Clicking a card's title opens its milestones in five columns, read from the card alone. Learned: a
  card written because the file moved a milestone still owes a history line; the first cut skipped
  it, and the test that pinned the exact history caught it.
- `board-stays-live` — archived as `openspec/changes/archive/2026-11-03-board-stays-live/`; the
  change requested at attestation. Archive closes with `--hat <product|maintainer|dev|devops>` from
  the initiative's worktree before cleanup; repropose passes `--hat <product|maintainer>`; propose
  writes a new descriptor at `exploring` and reaches `proposed` through `advance`; repropose and
  reexplore supersede milestones as `[~]`, before the move. `moveCard` carries the file's milestones
  onto the card. A rule now runs, for every row of `TRANSITIONS`, the command its workflow's
  template writes, from the row's `from` state. The three bars attestation found unasserted have
  tests: two single-branch clones on different branches render one board through their own
  playbooks; clicking a card's title opens its milestones; the playbooks run with only git and the
  shell's utilities on `PATH`. The page runs under a DOM stand-in (`test/helpers/board-dom.ts`), not
  a DOM library, which would have rewritten the `6.0` lockfile. `docs/` describes the live board.
  Learned: **a rule that reads a template is not a rule that runs it** — "the template mentions
  `--to completed`" passed while archive's command was refused. Repropose and reexplore had also
  written superseded milestones as `[x] ~~name~~`, which every parser reads as done.

### Change requested — 2026-11-03

Requested by Ivan Lee at attestation: **ready-for-attestation → building**. Not attested. The work
below is missing, and building it is all that is needed; the strategy and the ADRs stand. Found by
reading the bars against their tests, and by checking at the operator's request which workflows move
the card.

**Workflows that leave the board stale.**

1. `/opsp:archive` runs `opensprint advance <initiative-name> --to completed` with no `--hat`.
   `attested → completed` is a handoff, so the CLI refuses it and neither the initiative nor its
   card moves. Every finished initiative stays in Attestation.
2. `/opsp:repropose` runs `opensprint advance <initiative-name> --to proposed` with no `--hat`. From
   `building` that is a handoff, and is refused.
3. `/opsp:propose`, started from explore, writes `state: proposed` into the descriptor by hand, so
   its own `advance --to proposed` is refused as "Already 'proposed'" and no card exists until
   apply's `claim`. Propose should move the state only through `advance`.
4. `/opsp:repropose` and `/opsp:reexplore` edit milestones in the file, and the card's milestones
   catch up only at the next `kanban stage` or `seed --resync`. The move that follows the edit
   should carry them onto the card.
5. Unverified: `/opsp:archive` removes the initiative's worktree before it runs `advance`, which
   resolves the initiative from the current directory. Confirm the order works, or change it.

Each needs a test that runs the command as the template writes it, from the state the workflow
starts in. "Every workflow moves state through a command" passes today while 1–3 are refused.

**Bars whose tests do not assert them.**

- DS-LIVE-BOARD, primary: both clones in the tests are on `main`. Add one with two checkouts on
  different branches, neither fetching the other's, where a move pushed from one appears in the
  other's render.
- DS-LIVE-BOARD, drill-down: the milestone columns and stage data are tested; opening an initiative
  onto them is not.
- DS-RUNTIME-LESS-BOARD: the playbooks run with the full `PATH`, node included. Run them with a
  `PATH` holding only git and the shell's utilities.
- DS-LIVE-BOARD, guardrail: asserted by its tests. Not recorded as met, because no CI artifact
  exists yet.

**Documentation.** `docs/` does not describe the live board. It should present `advance`, `claim`
and `kanban stage` as what the workflows run, and `opensprint kanban init` (once) and
`claim --take-over` as the only commands a person types. A draft was proposed at attestation.
